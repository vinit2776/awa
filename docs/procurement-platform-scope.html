01 — Overview

What this is

Replaces a paper- and WhatsApp-fragmented approval process with one digital flow: requisition → sourcing → purchase order → receipt (goods or service) → invoice match → payment, with role-based approval at every gate and a full audit trail. Delivered as a service to multiple customer organizations from one codebase, with strict data isolation between them.

Three ideas run through every section below and should stay consistent as the build progresses:

  • Configurable, not hardcoded. Approval chains, roles, and catalog categories are tenant-authored data, not application logic.
  • Trust is layered, never a single control. PO authenticity, fraud detection, and asset custody all rely on several independent, mutually reinforcing checks rather than one gate.
  • Nothing terminal without a record. Rejections, ad-hoc approver additions, and catalog merges all preserve history — the system self-corrects without deleting evidence of how it got there.
02 — Roles

Roles & permission layers

Roles are tenant-configurable permission sets built from a shared template, not fixed code paths. Every user can raise a requisition by default; everything past that is scoped.

Platform layer

  • Platform super admin — tenant lifecycle, billing, feature flags, resource usage, API keys
  • Platform support — time-boxed, logged impersonation only

Tenant & procurement layer

  • Tenant admin — configures approval rules, roles, branding, integrations
  • Requestor — every user, by default
  • Department head / budget owner, procurement officer, goods/service receiver, finance approver, CFO / controller, approval delegate

Asset & external layer

  • Asset custodian, facilities/maintenance manager, internal technician
  • Vendor admin, vendor user, external technician (ticket-scoped magic link, not a standing login)
  • Internal auditor — read-only across everything, no transact rights
Segregation of duties — enforced by default, tenant-toggleable: a requestor can't approve their own PR; an approver can't be the goods/service receiver on that PO; the receiver can't be the finance approver who matches the invoice.
03 — Core flow

Procurement workflow & goods/services branching

One PR can carry both goods and service lines. Each line branches independently after the PO is issued — goods need a physical receipt, services need an acceptance sign-off — then both re-converge at invoice matching.

  • Goods line: PO line → delivery → goods_receipt_note (partial/split supported) → quality check → accept or reject-and-return
  • Service line: PO line → milestone or full-completion acceptance → sign-off by whoever actually received the service
  • Hybrid: goods delivery followed by an installation/setup service line on the same PO

04 — Approvals

Approval engine

A PR's required approvers are assembled from rules at submission, then stay open to ad-hoc additions until fully cleared — not a single fixed chain.

approval_rule the configurable matrix
FieldTypeNotes
category_id / department_id / cost_center_idfk, nullablenull = wildcard — this is how a rule becomes "global" vs "specific"
min_value / max_valuedecimalrange this rule applies in
combination_modeenumadditive (default, unions with other matches) · exclusive (overrides lower-priority rules)
requisition_approval_requirement the frozen instance for one PR
FieldTypeNotes
sourceenumrule · ad_hoc
assigned_user_idfkresolved person, frozen at add-time
added_by_user_id / reasonfk / textreason required when source = ad_hoc; only a currently-pending approver may add a row
group_no / group_sequenceintsame group = parallel, e.g. director + IT head both required; later group = gated behind earlier one

Example: an IT-asset PR matches a category rule (IT head + director, parallel) with no upper value bound; a chair PR under a threshold matches only a department-head rule. Either approver on the IT PR can still pull in a security reviewer ad hoc, with a reason logged.

Rejection

Two distinct outcomes, not one: rejected with defects returns to the requestor to fix and resubmit (other approvers' decisions stand unless value/category changed materially); rejected and closed requires a mandatory reason and ends the PR permanently.

05 — Vendor trust

PO authenticity — the vendor's side

A vendor should never have to trust a PDF or an email. Every layer below is independent, so no single compromised channel breaks the chain: digital signature + hash unique QR verification immutable audit entry signatory registry

  • Vendor portal is the source of truth — not the emailed PDF. Vendors log in (or scan a QR) to confirm a PO, never act on the document alone.
  • Bank-detail changes are locked after onboarding and can only change through an out-of-band callback to the vendor's originally registered number — never via email or PO amendment. This is the highest-value control: most large procurement fraud is a bank-swap, not a fake PO.
  • Authorized-signatory registry lets a vendor cross-check who at the company can approve a PO at a given value.
  • Value-escalated verification — small POs need only the portal check; above a configurable threshold, a callback or recorded confirmation is required before the vendor proceeds.
06 — Fraud

Duplicate & fraud detection

Invoice-number matching alone catches almost nothing. Layered detection runs at both invoice intake and pre-payment:

LayerCatches
Fuzzy matchSame vendor + similar amount within N days, different invoice number — the classic resubmission
Document fingerprintingPerceptual hash of the uploaded file — same scan, one field edited
Bank-account watchSame account number across multiple "different" vendors — shell-vendor pattern
Behavioral anomalySpend spikes, amounts clustered just under an approval threshold, off-cadence submissions
Risk scoringCombines the above into an explainable score, routed to human review — never an auto-block
Open tension — the bank-account watch is far stronger compared across tenants, which conflicts with strict per-tenant isolation. Needs an explicit, opt-in, anonymized shared-signals layer, deliberately separate from tenant data itself. See §12.
07 — Catalog

Self-regulating catalog

Any user can create a new item while raising a PR, so the catalog needs active duplicate suppression, not after-the-fact cleanup.

  • Prevent at creation: fuzzy string + phonetic + semantic-embedding search against existing items as the user types, surfacing "did you mean…" before a new entry is allowed
  • Don't block, flag: new items go live immediately as unverified, queued for a catalog steward
  • Periodic clustering surfaces likely-duplicate groups for one-click merge
  • Merges remap, never delete — old item IDs point to the canonical one so historical spend analytics stay intact
  • Usage-weighted ranking in typeahead so people naturally pick the existing entry over typing a new one
08 — Assets

Asset lifecycle & QR

Goods above a tenant-configured category/value threshold auto-register as assets at GRN confirmation, each getting a QR-linked digital passport.

  • Passport contents: procurement trail, custody chain, warranty status, service/repair log (each entry tagged AMC-covered or billable), linked AMC contract
  • AMC as its own contract entity — one contract can cover many assets; auto-renewal alerts; auto-check coverage before approving a repair spend
  • Two-tier QR access, one physical label: a signed-in, role-permissioned user sees the full passport; an unauthenticated scan sees name/category/status only, plus report an issue / request maintenance actions
  • Third tier for external repair vendors: a time-boxed magic link scoped to one open service ticket — never standing portal access
09 — Delivery

PWA & performance

  • Web Push for approval/alert notifications — no app-store dependency, reaches every authorized user
  • Domain-verified sign-up by default (only verified company email domains can register); IP/VPN allowlisting available as an enterprise-tier option
  • Service-worker app-shell caching, server-side catalog search (the catalog never ships client-side), paginated/virtualized queues
  • Mobile-first for the field roles that need it most — facilities/maintenance and goods receivers work from a phone, not a desk
10 — Platform

Multi-tenancy & isolation

  • Every record scoped by tenant_id, enforced at the database layer (row-level security), not just application-code filtering
  • Per-tenant encryption keys; isolated object-storage paths; tenant-scoped auth tokens that structurally cannot cross tenants
  • Stronger isolation tiers (schema- or database-per-tenant) available for enterprise/regulated customers on request
  • Platform super admin: subscription/billing, feature flags per tenant, resource-usage visibility, API key issuance, logged/time-boxed support impersonation

Integrated vs. split infra

The storage decision made for customer #1 (§15) generalizes into a real platform capability, not a one-off: two offering modes, selectable per tenant, not hardcoded platform-wide.

  • Fully integrated (default). Platform owns and bills for everything — hosting, storage, and all intelligence-API usage (OCR, embeddings, fraud scoring) bundled into subscription pricing. One number, no infrastructure decisions for the customer. Platform bears all usage-cost risk and prices to cover it.
  • Split infra (opt-in). Customer brings and directly pays for storage and/or their own AI-API accounts (OpenAI, an OCR provider); the app operates using the customer's credentials, so that vendor bills the customer directly, not the platform. Removes the platform's exposure to usage volatility and keeps the subscription flat regardless of the customer's actual document volume — but shifts real setup/management burden onto the customer (creating and rotating API keys, a second bill to reconcile) and reintroduces the credential-custody security surface (their keys, encrypted, held by the platform) already flagged for storage.

Model as a per-tenant setting, mirrored across both resources — storage_mode and intelligence_api_mode, each platform_managed or customer_provided — not a platform-wide fork. A technical, control-conscious customer can go split on storage while staying fully integrated on the intelligence add-ons until they actually buy that tier; a less technical customer defaults to fully integrated on both.

Where this actually bites: the moment a customer buys the fraud-detection or catalog-dedup add-on (§06/§07), that's the natural decision point to offer both modes — integrated (platform runs the AI calls, marks the API cost into the subscription price) or split (customer supplies their own key, pays a lower subscription since there's no cost pass-through, but owns the account management). Worth being honest that split-infra-for-APIs is a much bigger ask than split storage for a non-technical buyer — managing an OpenAI or OCR account, watching rate limits, and reconciling a second bill is real friction for a company whose core business isn't software. Likely a stronger fit for larger, IT-staffed enterprise customers than for customer #1.

12 — Open

Decisions to make before phase 0 locks

Isolation tier default

RLS-with-shared-database for all tenants, or schema/DB-per-tenant for enterprise customers from day one? Changes phase 0 cost significantly.

"Closed domain" access

Tenant-branded private subdomain, or network-level restriction (IP/VPN, domain-verified signup) — or both? Confirmed lean is the latter, given sensitivity.

Cross-tenant fraud signals

Bank-watch and behavioral fraud detection get stronger across tenants, which cuts against strict isolation. Needs explicit opt-in design, not a default.

Default approval group behavior

Should same-group approvers default to parallel (any order) with sequential the exception, or the reverse? Affects every tenant's first-run experience.
13 — Stack

Recommended tech stack

Chosen against two constraints the rest of this document keeps returning to: isolation has to be enforced at the data layer, not app code (§10), and the PWA has to stay light on a mid-range phone (§09). Everything below traces back to those two, plus the fact that the domain model — approval graphs, goods/service branching, audit trail — is deeply relational.

Fork points worth deciding now

Supabase vs. self-managed Postgres — Supabase bundles RLS tooling, auth, and storage, cutting real time off phase 0. Self-managed (RDS/Neon) gives more control if schema- or database-per-tenant isolation is coming sooner than phase 3 for a specific enterprise customer.
Monolith vs. early service split — recommend staying a single Node/TS modular monolith through phase 2, and splitting out only the Python fraud/ML service when phase 3 actually needs it. Splitting earlier than the work demands just adds deployment overhead.
Drizzle vs. Prisma — both work fine here; pick based on team familiarity. Drizzle maps more directly to the RLS session-variable pattern, Prisma has the bigger hiring pool and docs base.

This also resolves the isolation-tier question left open in §12: RLS on a shared database at launch, with schema- or database-per-tenant available later on the same schema design — Postgres supports both without a rewrite.

Three platforms, each doing what it's actually best at — chosen to avoid the four-provider sprawl (frontend host, DB host, Redis host, worker host) that a pure serverless-first plan tends to accumulate.

15 — Customer #1

Confirmed scope & pricing

First reference customer: managing director of an oil-extraction company, sole go-ahead authority, confirmed rollout plan. Real pain named directly: missed payments, delayed payments, double payments, unverified payments, unclear approval source, rework from lost paperwork, invoice recall. ~150 bills/month ongoing volume.

Base tier — "basic flow" (₹1.2 lakh/year)

Maps directly onto the phase-1 schema and sprint plan already built — the phase boundaries and the pricing-tier boundaries turned out to be the same boundary.

  • Requisition → approval (rule-based + ad hoc) → PO → invoice match → payment queue → audit log
  • Goods receipt: delivery-challan referenced, full or partial quantity
  • Service acceptance: a real confirmation step, deliberately lighter than goods — no delivery challan, no quantity/partial tracking, just a check that the work was actually delivered before invoice matching proceeds. Preserves the founding requirement (§01/§03): someone confirms receipt before payment, for goods and services.
  • Exact-match duplicate detection included free — a database constraint (vendor + invoice number), not a paid feature, since it directly addresses his named "double payments" pain at zero marginal cost
  • Document storage: he procures and pays for it directly — positioned as data control, not cost-sharing. Documents only (PDFs, photos); structured records (approvals, invoices, audit trail) stay in the platform database. This is the first instance of the general split infra tenant setting formalized in §10 — storage_mode = customer_provided; his intelligence_api_mode stays platform_managed until he buys an intelligence add-on.
Confirm before signing — no RFQ/vendor-quotation-comparison step is included in this description (PO appears to issue directly). Confirm that's intentional for v1 and not an omission.
